# 算法穿透

## 触发边界（强制）

- 仅在用户明确点名 `vt-algorithm-penetrate`、"算法穿透"，或显式指定本技能目录时执行本技能。
- 用户只提到算法调试、查看中间结果、解释算法等，但未点名本技能时，**不得**启用；按普通对话或其他已触发技能处理。
- 不要为了使用本技能而追问用户是否启用；只有用户主动点名才生效。

## 目标

协助用户真正理解并掌握一个具体的算法流。核心手段是把黑盒算法流变成可逐级查看的白盒数据流：

1. 用用户提供的参数与图像真实跑通算法流，拿到每个分析点的过程图与过程数据。
2. 以最终瑕疵位置为 ROI，反推它在各过程图中的位置与表现，完成数据变化的真实记录。
3. 追踪前置候选在后续哪些函数、被什么判断条件强化、补充、抑制或去除。
4. 输出以算法功能分析为主线的图文报告，解释每个功能模块的输入输出与关键判断；图像和 ROI 是说明功能的证据。

区分源码静态事实、既有运行证据与推断。默认不评价某张图是否漏检、误检，也不把被删除的候选自动认定为假目标；精度验收仅在用户另行要求且具有相应真值时开展。

## 用户需提供

1. 算法流位置：C++ VS2019 工程（默认主路线）或 HDevelop 脚本；指明入口函数/脚本。
2. 输入图像路径：单张即可分析。多张图时按缺陷类型/功能场景归纳总结，**不按图像序号逐张流水账**。
3. 运行参数：用户指定参数；参数硬编码在代码中时，确认以代码现值为准还是由用户覆盖。
4. 可选：额外指定必须分析的函数段（无论颗粒度拆分结果如何都必须覆盖）。

新采集缺输入时先向用户要齐，不要用猜测的图像或参数跑流程。仅更新已有报告时，先从现有 output、清单和报告读取来源，无需重复索要已明确的输入。

## 输出目录与产物

默认输出根目录：`<工程>/x64/output_算法穿透/<yyyyMMdd_HHmmss>/`（用户指定目录时遵循用户指定）。内部结构：

```text
output_算法穿透/<时间戳>/
  插桩备份/                 # 插桩前的原始源码/脚本副本，保持原编码与 BOM
  过程图/<分析单元名>/       # 每个插桩点落盘的图像 + 数据文件（csv/txt）
  ROI裁剪/<ROI名>/          # 各过程图中同一 ROI 的裁剪图
  <YYMMDD>算法穿透_<算法名>.md    # 穿透报告
  <YYMMDD>算法穿透_<算法名>.html  # 同名 HTML 版本
```

- 过程图文件名带序号与分析点语义，如 `01_01_高斯滤波后.png`，保证排序即流程顺序。
- 插桩代码中保存路径直接写当次输出目录的绝对路径，避免运行时环境差异导致落盘失败。

## 工作流程

### 先选择执行模式

- **新采集**：按阶段一至六执行，使用用户指定输入获取过程图与数据。
- **已有数据报告更新**：用户要求基于 output 优化、重新生成报告或明确“不重跑”时，只读取已有图像、掩膜、数值和必要源码；可重新裁剪、排版及核对统计，不编译、不插桩、不运行检测或测试、不修改参数。直接执行适用的阶段四与阶段六，不重复采集确认，也不执行源码还原。
- 已有数据不足以支持某个功能场景时，说明证据缺口；不为凑齐示例伪造过程图或自行重跑。若用户只修改命名、注释或可读性，按下文“源码变化后的报告刷新”处理。

### 阶段一：通读代码，输出分析拆分清单（默认必须等用户确认）

1. 通读算法流代码，按**功能与模块**拆分分析单元（不是按函数嵌套层数机械拆分）。
2. 输出清单，逐项给出：分析单元名称、涉及函数、插桩点位置、计划保存的过程图与数据。
3. 等用户确认后才进入插桩。用户明确说"无需确认分析点"时跳过确认直接执行。

### 阶段二：插桩

**C++ VS2019 路线（主）：**

- 插桩代码用统一宏开关控制（如 `ALGO_PENETRATE`），关闭后零开销、可整体还原：

```cpp
#ifdef ALGO_PENETRATE
// 算法穿透插桩：保存 <分析点语义> 过程图（任务 <时间戳>）
{
    cv::imwrite("<输出目录绝对路径>/过程图/02阈值分割/02_01_二值图.png", matBin);
}
#endif
```

- 插桩前：将被修改文件的原样副本放入 `插桩备份/`。
- **编码强制规则**：插桩前必须检测目标文件编码与 BOM 状态；插入的代码与中文注释必须以该文件原有编码写入（如 GBK 文件中不得写入 UTF-8 中文注释，否则乱码或编译失败）；无法可靠判断编码时先检测或询问，不得猜测后覆盖。新增代码注释使用中文。
- 变量命名遵循项目既有习惯（int 以 `n` 开头，bool 以 `b` 开头），插桩内临时变量不污染外部作用域（用独立块 `{}` 包裹）。
- 运行验证使用 Release 优化配置，调试信息保持 `/Zi` + 链接器 `/DEBUG`（与全局工程规则一致）。优先最小范围重编受影响模块。

**HDevelop 路线（辅）：**

- 用脚本内全局开关变量（如 `bPenetrateDump`）控制 `write_image` / `dump_window` 插桩。
- 脚本文件同样先备份到 `插桩备份/`，分析完成后还原。

### 阶段三：编译运行与采集

- 用用户指定的参数与图像运行算法流；每个插桩点保存：
  - 过程图（png/bmp）
  - 关键过程数据：区域数量、面积、灰度 min/max/mean、阈值、坐标、耗时等，落盘为 csv/txt
- 记录编译与运行中的异常；算法流跑不通时先解决运行问题，再继续穿透。
- 运行目录被占用需要独立环境时，按全局规则使用 `x64/Release_AI_<时间戳>`。

### 阶段四：ROI 反推与裁剪分析

1. **瑕疵 ROI**：以算法流最终输出的瑕疵位置（区域/矩形/坐标）为基准 ROI。
2. 将该 ROI 反推映射到每个过程图的相同坐标，裁剪对应窗口：
   - 正文使用紧凑裁图，围绕同一统计域内各展示阶段的有效响应收紧窗口，只保留解释局部结构所需的背景；不固定大幅外扩，不让最小显示框或空白画布淹没小目标。
   - 显示窗口与算法运算邻域分开，不能因展示裁剪改变算法数据。同行各阶段使用相同坐标窗口和倍率；小图应实际放大，二值掩膜优先最近邻显示。跨场景倍率不同时标明各自窗口或尺度。
   - 同时保留全图参照，放入折叠区或附录；正文优先用局部对照解释功能。
3. **候选抑制追踪**：以前置候选与后续区域的集合关系，追踪何时缩小、消失或被补回及对应判据。固定追踪域并明确面积统计范围，避免把邻近候选混入计数；差集表示被删除像素，不等同于已确认假目标。
4. 穿透链必须标注步骤编号和数据流关系：箭头表示先后处理；独立分支标“并行”，汇合标并集、交集或差集等实际运算。不可把并行信号拼成串行流程。
5. 结合各函数输入输出与过程数据，解释“数据为什么这样变”，而不是只罗列图像。具体版式见报告模板。

### 阶段五：还原与校验（强制）

1. 移除插桩代码（或用备份文件还原），脚本类同理还原。
2. **校验还原干净**：git diff（或与 `插桩备份/` 副本做字节对比），并核对文件编码与 BOM 状态与插桩前一致。
3. `插桩备份/` 中的副本保留在输出目录，供用户追溯。

### 阶段六：报告

按 `references/report-template.md` 的结构生成图文并茂的 Markdown 报告，并生成同名 HTML 版本（图片使用相对路径引用，与 md 共享，保证整个输出目录可拷走浏览）。要点：

- 每个关键结论配过程图或 ROI 裁剪图，图下写明"该图说明什么"。
- 正文按功能模块组织，解释功能、输入、输出、关键判断及其视觉效果，使用当前源码中的可读名称，区分强度图、二值区域与显示用过程图。
- 同类型缺陷或功能表现一起分析。例如“FuncA 的作用”下用三个有区别的场景展示补齐、保持、删除；示例数量服从实际证据，不强制每节凑足三种。
- ROI 穿透链与候选抑制链应覆盖，但可直接融入对应功能模块；完整 ROI 索引、逐对象明细、全图与运行日志放入折叠区或附录，避免逐图流水账和重复解释。
- 数据变化用真实记录表格呈现，来源标注插桩点。
- 图文生成后实际查看代表图与 HTML，检查目标占比、文字可读性、箭头与分支关系、图片链接及统计口径；不能只以文件存在作为排版通过。
- 区分“源码静态核对”“原采集实测”“推断”；报告更新不能把历史实测写成当前源码重新运行的结果。

### 源码变化后的报告刷新（沿用既有数据）

1. 将当前源码与采集时保存的源码快照比较，确认变更范围。仅命名、注释调整时，建立作用域明确的新旧标识符映射，并核对调用关系、判据、常量及运算顺序；可用去注释后的代码 token 对照辅助核验，不把文本相似度当作语义等价证明。
2. 同步正文、流程图、穿透图标题、参数名和代码行号，按新名称解释实际功能；保留原始采集文件名和键，提供“当前名称—类型／作用—旧采集键”对应表。不能只改正文而让图片继续沿用旧术语。
3. 注明采集时间与版本、当前源码版本／哈希及静态核对范围，并明确本次未重新编译或测试。若有逻辑变化或无法证明对应关系，仅引用仍有依据的历史结果，标明受影响部分；不将旧结果直接归于当前逻辑，不突破用户“不重跑”的限制。
4. 不用旧备份覆盖用户当前源码。保留原始证据；用户要求“重新生成一份”时另存有明确后缀的新版本及展示图，旧报告可继续打开。其他更新遵循用户指定的覆盖或保留方式。

## 分析颗粒度

以**功能与模块**为分析单元，两个禁止、一个补充：

- 禁止过大：多层函数嵌套时不得只分析最外层函数，必须下钻到有实际图像处理语义的层级。
- 禁止过小：不得为单个基础算子（如 Threshold 输入啥输出啥）单独成章；简单基础算子并入所属功能段内说明其参数与作用。
- 补充：用户指定分析的函数段必须额外覆盖，不受上述拆分限制。

判断标准：一个分析单元应对应"一个有明确视觉/数据效果的中间结果"（如"斑点提取模块：滤波+阈值+连通域"），且该中间结果值得裁图分析。

## 关键判断记录要求

每个分析单元必须写清：

- 判断条件原文（阈值数值、分支条件、参数名与当前值）。
- 该判断对数据的影响（通过/不通过分别发生什么）。
- 该判断控制候选的产生、范围、合并还是删除；需要讨论参数敏感性时说明依据或标注推断，不扩展为逐图精度评判。

## 多图输入处理

- 单张图即可完成完整穿透分析，无需对照图。
- 新采集时逐张执行；报告更新时直接复用已有记录。正文始终**按同类型功能／缺陷场景归纳**，样本编号只用于溯源，不作为主章节。

## 报告语言与文件命名

- 报告使用中文。
- 文件名：`<YYMMDD>算法穿透_<算法名>.md` / `.html`，YYMMDD 为当前本地日期（如 `260317`）。
- 同一采集数据的独立修订版可加语义后缀，如 `_功能分析`、`_源码可读化`；Markdown 与 HTML 同名并共享对应展示图。
